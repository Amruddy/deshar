# Deshar Design System

## Обязательный порядок

Перед UI-изменениями читать:

- `docs/roadmap/README.md`;
- `docs/work-plans/active/README.md`;
- `docs/work-plans/active/32-new-visual-design-plan.md`;
- `docs/specs/04-visual-rules.md`;
- релевантные specs из `docs/specs/02-feature-specs/` и `docs/specs/03-technical-specs/`.

Перед кодом коротко написать пользователю:

1. какие пункты будут изменены;
2. какие страницы или файлы будут затронуты;
3. дизайн это или функциональная логика;
4. какие проверки будут выполнены.

Если изменение затрагивает data-layer, права, actions, маршруты или продуктовую
логику, не смешивать его с дизайн-stage без отдельного work plan.

## Базовый стиль

Строить интерфейс как рабочую систему, не как лендинг:

- светлый зелено-серый фон приложения;
- белые или теплые поверхности блоков;
- глубокий зеленый основной акцент;
- спокойные янтарный, синий, красный и зеленый статусы;
- плотная, но не перегруженная сетка;
- минимум декоративных элементов;
- таблицы и списки вместо лишних карточек, когда пользователь сравнивает данные.

Использовать общий визуальный слой из `app/globals.css`. Не добавлять разовый
стиль в страницу, если его можно выразить через существующие классы:
`panel`, `section`, `table-wrap`, `data-table`, `button`,
`secondary-button`, `status`, `info-row`, `metric-card`.

## Shell и навигация

Desktop:

- левая навигация остается главным app-shell;
- верхний sticky-блок с ролью/email не нужен, если эти данные уже есть слева;
- нижний блок пользователя в sidebar показывает роль, имя, email, организацию,
  профиль и выход;
- нижний блок пользователя должен стоять в закрепленной нижней зоне sidebar;
- если высоты не хватает, прокручивать список разделов, а не user-card.

Mobile:

- использовать нижнюю компактную навигацию;
- не перекрывать основные действия;
- проверять, что длинные labels не ломают layout.

## Таблицы и списки

Таблицы должны быть читаемыми и похожими на design map:

- округленная рамка всей таблицы;
- спокойный заголовок;
- нормальные переносы текста;
- без наложения текста на текст;
- длинные названия групп, курсов, контекстов, оплат и учеников должны переноситься;
- status badges не должны сжимать соседний текст;
- actions в строках должны переноситься вниз или в несколько строк, если места мало.

На mobile таблица может перейти в горизонтальную прокрутку или адаптированный
список. Для журнала предпочтителен адаптированный список одного урока.

## Журнал

Журнал преподавателя - ключевой экран.

Правила:

- месячный журнал показывает только даты реальных уроков, не все дни месяца;
- desktop-вид должен читаться без горизонтальной прокрутки для обычного месяца;
- строки - ученики, колонки - даты уроков;
- отметки компактные: `П`, `Н`, `У`, оценка или короткая запись;
- пустая отметка прошедшего урока читается как присутствие, если запись сохранена;
- администратор видит тот же журнал только для просмотра;
- не вводить статусы урока "начат" или "завершен".

Если пользователь просит ручной ввод оценок/комментариев прямо в ячейке, сначала
проверить текущую data model и actions. Если поля или серверная логика не готовы,
это функциональный stage, а не CSS-правка.

## Роли и страницы

Admin:

- страницы списков должны начинаться с таблицы и действия рядом с заголовком;
- группы, курсы, ученики, преподаватели и оплаты должны использовать общий
  table/status/button язык.

Teacher:

- главный экран должен быстро вести к ближайшим занятиям, группам и журналу;
- shortcut журнала должен быть спокойным рабочим блоком, а не тяжелой плашкой;
- журнал и уроки не должны смешиваться с лишними пояснениями.

Student:

- домашние задания, материалы, прогресс, посещаемость и оплата должны быть
  понятными и спокойными;
- если посещаемости еще нет, показывать empty state, а не набор нулей, который
  выглядит как техническая ошибка;
- ученик не редактирует учебные записи.

## Проверки

После UI-изменений запускать минимум:

- `git diff --check`;
- `npm.cmd run lint`;
- `npm.cmd run build`;
- `npm.cmd run smoke:roles`, если dev-сервер доступен.

Для ручной проверки открыть:

- `/login`;
- `/admin/students`;
- `/admin/groups`;
- `/admin/payments`;
- `/teacher`;
- `/teacher/groups`;
- журнал группы;
- `/student`;
- `/student/attendance`;
- `/student/homework`;
- `/student/payments`.

Если `smoke:auth` падает из-за внешнего состояния Supabase Auth, зафиксировать
точную причину отдельно и не маскировать ее CSS-изменениями.
